# src (Svelte frontend)

- Svelte 5 `$derived` class fields never invalidate outside a live component/effect-root context — a bare `new SearchScreen()`-style instance in a vitest test computes it once and never recomputes. Use a plain getter instead when a value derived from `$state` fields needs to work both inside `$effect` and from a bare test instantiation.
- Svelte scoped `<style>` never reaches markup rendered by a child component — when extracting a shared block (e.g. a button row) into its own `.svelte` file, move its CSS into that new component too, don't leave it in the parent's stylesheet.
- Svelte 5 warns `state_referenced_locally` when a `$props()` value is passed as a one-shot constructor/call argument (e.g. `new XScreen(storyId, ...)`) — not when read inside a function body. The `*Screen` classes (`SearchScreen`/`BookmarksScreen`/`ReaderScreen`/`SearchModalScreen`) hit this every time; if the prop genuinely can't change during that mount (confirm via how the parent conditionally mounts it), silence with `// svelte-ignore state_referenced_locally` + a one-line why, don't restructure to chase the warning away.
- `src/routes/debug/+page.svelte` deliberately uses raw `invoke()` for commands, not `api.ts`-style command wrappers (the one `api.fetchChapterAndWait` call, for bulk prefetch, is the exception) — it's a debug harness for exercising Tauri commands directly, don't fold command dispatch into shared seams during a refactor. Pure non-command utilities (e.g. `pacedLoop.ts`'s `jitterDelay`/`sleep`) are fine to share.
- A `*Screen` class that starts background work (a prefetch chain, a polling loop) needs a `dispose()` that bumps its generation token, called from the owning component's `onDestroy` — nothing else stops it on unmount (`ReaderScreen` kept prefetching after Back until this was added).
- Failures shown on the page banner go through `ErrorBanner` (`errorBanner.svelte.ts`), one message per operation key: `banner.run(key, prefix, op)` for anything that throws (clears on success; `{ clearOn: "start" }` for bulk jobs), `banner.report(key, text)` for a job's partial failure. Only the same key succeeding, or the user's ×, removes a message — so no ordering rule about `reloadAll()`. A new banner-reporting operation needs a new `BannerKey`; tests assert on `banner.messages`, not a callback.
